4隐私表单 审核重灾区 · 慢一点填

这一步决定了你是「一周过」还是「来回三趟」。三块内容：单一用途、权限理由、数据使用。

4.1 单一用途（Single purpose）

把用户提供的文本插入当前网页的代码编辑器（CodeMirror、Monaco、Ace、textarea、contenteditable）， 作为「网站禁用粘贴」时的替代输入方式。

4.2 权限理由（Permission justification）

三个权限，一条都不能空着。理由要讲技术上的非它不可，不是「我需要它」。

【scripting】 用于在用户点击工具栏图标后，把 page/ 目录下的脚本注入当前标签页。 注入必须使用 world: "MAIN"：CodeMirror / Monaco / Ace 的编辑器实例是页面脚本挂在 DOM 元素上的 自定义属性（el.CodeMirror、el.env.editor），扩展的隔离世界读不到这些属性，也就无法调用编辑器 自带的插入接口。注入只在用户点击图标后触发，不会在后台或页面加载时自动执行。 【activeTab】 用来替代 host_permissions，实现权限最小化。用户点击扩展图标时，浏览器才临时授予当前标签页的 访问权；切换标签页或关闭页面后自动失效。用户不主动使用扩展时，扩展对任何网页都没有访问能力。 【storage】 把用户正在编辑的草稿和最近 10 条插入记录保存在本地 chrome.storage.local。 因为插入时页面会抢走焦点、弹窗通常会自动关闭，没有草稿保存会直接丢失用户输入。 只写本地，不使用 storage.sync，不涉及任何上传。

4.3 远程代码 / 数据使用

  • 远程代码：选 否。所有逻辑都在 zip 里，没有 eval、没有动态 import。
  • 数据使用：九项全部不勾。草稿和历史只写本地，不传输，所以算「不收集」。
✓
「没有 host_permissions + 只在点击图标时拿 activeTab」是这个扩展最大的合规优势。 在单一用途和权限理由里主动讲出来，审核员会明显省事。

4.4 隐私政策 URL

必填。文件已经写好在 store/privacy-policy.md，中英双语。把它变成一个网址，三种做法：

做法地址长什么样耗时

6认证备注与提交 通过率的胜负手

Notes for certification 是给审核员看的手册。这个扩展有个特点：不点图标就什么都看不到。 不写清楚，审核员很可能打开页面、发现没反应、直接判「功能不工作」。

这是一个开发者工具：当网页上的代码编辑器禁用了粘贴，用户可以点击扩展图标， 把文本直接插入编辑器。 【为什么必须先点击图标】 扩展没有 host_permissions，只申请了 activeTab。这是刻意的权限最小化设计： 在用户点击工具栏图标之前，扩展对任何网页都没有访问权限。 所以测试时请先点击图标，再观察效果 —— 这不是功能缺陷。 【约 2 分钟的测试步骤】 1. 打开 https://codemirror.net/try/ （CodeMirror 6 官方示例页） 2. 在编辑器里点一下，让光标落在代码区 3. 点击工具栏上的「贴进去」图标。弹窗打开后，顶部状态标签会显示识别结果， 例如「已聚焦 CodeMirror 6」 4. 在弹窗的输入框里粘贴一段文字，例如：console.log('hello') 5. 点击「插入」按钮，或按 Ctrl + Enter 6. 文字应当出现在编辑器里；页面右下角出现绿色提示条； 弹窗可能自动关闭 —— 因为插入时页面抢走了焦点，这是正常现象 7. 再次点击图标，点「历史」按钮，可以看到刚才那次插入记录 【其他可测站点】 · Monaco —— https://microsoft.github.io/monaco-editor/playground.html · Ace —— https://ace.c9.io/ · 普通输入框 —— 任意包含 textarea 的网页 【以下情况显示失败是预期行为，不是 bug】 · 在 edge:// 开头的页面、Edge 加载项商店、PDF 阅读器上，任何扩展都无法注入， 弹窗会显示「受限页面」 · 页面里只有 iframe 内的编辑器时，v1 不支持，弹窗会明确提示 · 只读编辑器会被识别出来并跳过 【隐私】 扩展不发起任何网络请求。草稿和历史只写入本地 chrome.storage.local。 没有远程代码、没有分析统计、没有第三方 SDK。

7审核之后

通过了

扩展会出现在 Edge 加载项商店，用户搜得到、装得上，后续版本自动更新。 首次审核一般 1–7 个工作日。

可以在详情页补宣传图、改描述——这些不用重新传包。

被拒了

不封号。邮件会指到具体条款，改完重新提交即可。

最常见的两类：权限理由写得太敷衍、单一用途描述太宽。对策见附录。

发新版本

改完代码，把 manifest.json 的 version 加一，然后：

python store/build-package.py

把新 zip 传到 Packages 页，提交。版本号必须比上一版大，否则会被拦。

!附录 · 五个风险与对策

① 「绕过」这个词

商店里能搜到 Bypass Quora Pop-ups 这类扩展，说明「bypass」本身不是红线。 但描述里不要出现破解、付费墙、反检测、去水印这类词——那才是真雷区。

已经在 listing-zh.md 里把措辞软化成「替代输入方式」， 并给了一句更温和的简短描述建议。要改的话现在改，上传后就只读了。

② 审核员可能「测不出功能」

没有 host_permissions 意味着：不点图标，扩展什么都做不了。 审核员如果按常规套路打开页面等效果，会以为它坏了。

对策：Notes for certification 里把「必须先点图标」放在第一段，配 2 分钟分步流程。

③ 没有公网演示页

你的 demo/ 只能在本地跑。审核员不会 npm run demo。

对策：Notes 里用了三个公开可访问的官方示例页（CodeMirror、Monaco、Ace）， 足够验证插入能力。想把自家演示页也放上去，就发 GitHub Pages：

# 把 demo 复制成 docs，GitHub Pages 从 /docs 发布 cp -r demo docs git add docs store && git commit -m "chore: 商店素材与演示页" git push # 然后 仓库 → Settings → Pages → Source: main / docs
!
这一步会推到 GitHub 公开仓库，先确认你愿意公开这些文件。 store/ 里没有敏感信息，但推送前还是自己扫一眼。

④ iframe 与自研编辑器

v1 不支持 iframe 里的编辑器。描述里已经写成「已知限制」—— 主动交代限制比被审核员发现要安全得多，也少一堆差评。

⑤ 版本号与包一致性

每次重传 zip，version 必须递增。忘了改会直接卡在提交环节。 build-package.py 的文件名带版本号，扫一眼就知道传的是哪个。
